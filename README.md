# Barista

**A browser-based toolkit for inspecting Java code.**

Drop in a `.zip` of Java sources and get a UML class diagram back — generated by
static analysis, in your browser, with nothing uploaded anywhere.

## What it does

You have a Java project and you want to see its shape — which classes exist, how
they relate, where the inheritance goes, what owns what. Barista reads the
source and draws it.

The first tool in the kit is a **UML class diagram generator**. It identifies
your types and infers the relationships between them:

| Relationship   | Notation          | Inferred from                                      |
| -------------- | ----------------- | -------------------------------------------------- |
| Generalization | hollow triangle   | `class A extends B`                                |
| Realization    | dashed + triangle | `class A implements B`                             |
| Composition    | filled diamond    | `A` creates its `B` internally and never shares it |
| Aggregation    | hollow diamond    | `A` receives its `B` from outside                  |
| Association    | plain arrow       | `B` is a field of `A`                              |
| Dependency     | dashed arrow      | `B` appears only as a parameter, return or local   |

Multiplicity comes from the field's type: `List<Order>` yields `0..*`, a plain
`Order` yields `1`.

### It shows its work

Every relationship on the diagram carries the **evidence** that produced it —
the file, the line, and a plain-language reason:

> `Deck` → `Card` · composition
> Field `cards` is instantiated in the constructor (`Deck.java:14`) and never
> assigned from outside the class.

This matters because one part of the analysis is genuinely a judgement call, and
pretending otherwise would be dishonest. **Composition and aggregation look
identical in the syntax** — both are just a field. The difference is semantic:
who controls the object's lifecycle. Barista applies the standard heuristic
(created internally → composition; received from outside → aggregation), which
is right most of the time and wrong some of the time.

So instead of hiding that behind a confident-looking diagram, the tool tells you
what it saw and lets you overrule it. A tool that explains its reasoning teaches
you something. A tool that says "trust me" does not.

## Your code never leaves your machine

There is no backend. No upload endpoint, no server, no database, no account.
Unzipping, parsing, type resolution, layout and rendering all happen in your
browser tab, in JavaScript and WebAssembly.

This is an architectural decision, not a promise: there is no server to send
code to, so there is nothing to trust. You can verify it — open the network tab
and watch nothing happen. See [ADR 0001](docs/adr/0001-client-side-only.md).

## How it works

```
  file.zip
     │
     ▼
 ┌─────────┐   ┌─────────┐   ┌───────────┐   ┌─────────┐   ┌─────────┐
 │   zip   │──▶│  parse  │──▶│  resolve  │──▶│  infer  │──▶│  model  │
 └─────────┘   └─────────┘   └───────────┘   └─────────┘   └─────────┘
  unpack &      tree-sitter    symbol table   relationship   the diagram
  filter        → syntax       → semantics    rules          + evidence
                                                                 │
                                        ┌────────────────────────┤
                                        ▼                        ▼
                                  ELK layout              Mermaid / PlantUML
                                  + SVG render            export
```

The interesting stage is `resolve`, and it is worth explaining why.

A parser gives you **syntax, not semantics**. It will tell you that a field has
type `Engine`; it will not tell you _which_ `Engine` — the one in your package,
the one you imported, or a third one with the same simple name in a different
package. Turning a simple name into a fully-qualified type means building a
symbol table out of package declarations, explicit imports, wildcard imports,
same-package visibility, implicit `java.lang`, and nested types like
`Outer.Inner` — with Java's own precedence rules deciding the ties.

That, not parsing, is the hard part of this project. Real code is ambiguous, and
some types are genuinely unresolvable because they live in a jar you do not
have. Barista treats those as **diagnostics you can read**, not as crashes: one
unresolvable type does not stop the other four hundred from being analysed.

## Getting started

Requires Node ≥ 24.15 (pinned in `.nvmrc`) and pnpm 10.

```bash
git clone https://github.com/FlorianLucchini/barista.git
cd barista
nvm use          # picks up .nvmrc
pnpm install
pnpm dev         # http://localhost:4200
```

Or with Docker:

```bash
docker compose up --build
```

## Project structure

```
barista/
├── packages/core/       Analysis engine — pure TypeScript, zero framework deps
│   └── src/
│       ├── zip/         Unpack and filter Java sources
│       ├── parse/       tree-sitter → our own syntax model
│       ├── resolve/     Symbol table, simple name → fully-qualified type
│       ├── infer/       Relationship rules, each carrying its evidence
│       ├── model/       The ClassDiagram model
│       └── export/      Mermaid and PlantUML serialisation
│
├── apps/web/            Angular 22 interface — upload, layout, SVG rendering
│
├── docs/
│   ├── features/        One page per user-facing feature
│   ├── adr/             Architecture Decision Records
│   └── internal/        Contributor docs, design system, roadmap
│
└── .claude/             Agent harness: rules, skills, agents, hooks
```

### The boundary that matters

`packages/core` must never import Angular, the web app, or a DOM-only API. The
engine has to run inside a Web Worker and under plain Node, so that constraint
is load-bearing rather than aesthetic — and it is **enforced**, not trusted:

```bash
pnpm deps:check   # dependency-cruiser; fails the build on violation
```

This is the same rule as "the model must not depend on the view", with teeth. A
practical consequence: the UI framework is a cheap decision to reverse. Swapping
Angular for something else would rewrite `apps/web` and leave the engine — the
hard part — untouched.

### Test-driven, strictly

Every behavioural change starts with a failing test that is **run and seen to
fail** before any implementation exists. The engine is deterministic — the same
Java in, the same model out — which makes fixture-driven testing both easy and
obviously correct: a directory of Java files goes in, an expected model comes
out.

Details in [`.claude/skills/tdd-cycle/SKILL.md`](.claude/skills/tdd-cycle/SKILL.md).

### Design principles, enforced

The codebase follows the design principles from FIUBA's _Paradigmas de la
Programación_ — SOLID, DRY, KISS, YAGNI, Tell Don't Ask, the Law of Demeter,
low coupling and high cohesion — written out with TypeScript examples in
[`.claude/rules/design-principles.md`](.claude/rules/design-principles.md).

Sometimes the principled version is genuinely worse. That is allowed, but it has
to be argued in the code:

```ts
// PRINCIPLE-EXCEPTION: OCP
// Why: the six UML relationship kinds are fixed by the specification, so a
//   closed union is honest here and gives us exhaustiveness checking for free.
// Alternative considered: a renderer class per kind; rejected as ceremony over
//   a stable, closed set.
// Revisit: if relationship kinds ever become user-extensible.
```

`pnpm principles:ledger` collects every one of these into a report, so
exceptions stay visible instead of quietly accumulating. An exception without a
real argument is a violation with extra paperwork.

## Built with

Every choice below was made from measurements, not impressions — the numbers are
in the [ADRs](docs/adr/).

| Concern   | Choice                         | Why                                                                                 |
| --------- | ------------------------------ | ----------------------------------------------------------------------------------- |
| Parsing   | `tree-sitter-java` (WASM)      | 203 ms for 471 files; declarative queries beat hand-walking a CST                   |
| Layout    | `elkjs` in a Web Worker        | The only option that routes edges orthogonally — the UML look                       |
| Rendering | Hand-written SVG + `d3-zoom`   | Full control of the aesthetic, and PNG export needs clean markup                    |
| Animation | `motion`                       | Spring physics; `@angular/animations` is deprecated                                 |
| UI        | Angular 22, zoneless + signals | Vitest built in, and DI that matches the project's OOP thesis                       |
| Styling   | Tailwind v4 + custom tokens    | Design tokens in [`docs/internal/design-system.md`](docs/internal/design-system.md) |

## Limitations

Worth knowing before you file a bug:

- **Source only.** No `.class` files, no Maven or Gradle dependency resolution.
  Types from libraries you do not ship as source resolve as external.
- **Composition vs aggregation is heuristic.** See above. The evidence panel
  tells you what it based the call on.
- **Browser-bound.** Very large projects are limited by tab memory and CPU.
  Parsing and layout run in Workers so the UI stays responsive, but there is a
  ceiling.
- **Java 21 syntax.** Newer preview features may not parse.
